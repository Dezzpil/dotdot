# Контуры, цвет и лестница вариантов точек

Статус: согласовано (развилки закрыты вопросами); оба этапа реализованы и проверены — тесты и браузер. Что разошлось с текстом — в «Отклонениях» после каждого этапа.
Предыстория: [decisions.md](decisions.md).

## Что не так сейчас

| Проблема | Где | Почему |
|---|---|---|
| Точек то мало, то слишком много | `pipeline.py:LEVELS`, `dots.choose_eps` | Число точек — следствие уровня: допуск упрощения фиксирован (5.0/2.0/1.0 pt), а потолок (50/150/320) только обрезает сверху. Бинарный поиск включается лишь при превышении потолка — попасть в *целевое* число алгоритм не умеет |
| На рисунке несколько объектов, контур один | `strokes.outline_edge_ids` | Заливка дырок по всей маске → берётся **самая большая** связная компонента → точки только у её границы. Второй объект целиком уезжает в линии |
| Все точки одного цвета | `render.INK/ACCENT` | Цвет не несёт смысла; «серии» A1/B1 — это штрихи, а не объекты |
| Примеры вида «173+147» | `dots.math_expr` | Пример строится от сквозного номера n, потолка нет |
| Один job = один лист | `worker.py`, `job-view.ts`, `JobScreen.tsx` | Выбора плотности нет вообще |

## Принятые решения

| Развилка | Решение |
|---|---|
| «Для кого» (малыш/школьник/взрослый) | **Остаётся.** Уровень задаёт оформление (радиус точек, шрифт, мин. отступ, порог деталей, сложность примеров), число точек — отдельная ось |
| Как считаем варианты | **N отдельных задач в очереди**, не один job с N результатами |
| Повторный анализ и дубли вариантов | **Сначала служебная задача анализа**, она знает реальный предел точек и сама ставит задачи-варианты |
| Что раскрашиваем | **Цвет = объект** (силуэт + его детали), нумерация внутри объекта своя, с 1 |
| Что считать объектом | **Связные компоненты + вложение и близость**: мелкая часть внутри силуэта крупной или почти касающаяся её — та же группа и тот же цвет |
| Лестница | **5 вариантов, шаг ×1,35** внутри диапазона уровня; своё число T центрирует лестницу: 0,8T / T / 1,25T |
| Примеры и лимит | Лимит **на ответ** (номер точки), по умолчанию 100, вынесен в параметры. Действует только в режиме примеров. Крупный контур **упрощается** (реже точки), чтобы уложиться в лимит; контур не дробится |
| Нумерация и ч/б | **Три режима**: одна цепочка с «прыжками» / по контурам цветом / по контурам буквами (A1, B1…). По умолчанию — цветом |
| Очерёдность | **Этап 1 — алгоритм** (объекты, цвет, нумерация, лимит, plan v2, редактор), **этап 2 — варианты** (анализ, лестница, экран выбора) |
| Окружение для проверки | **Гибрид**: Redis и воркер в Docker (исходники воркера примонтированы), API и web локально, проверка в браузере |

## Этап 1 — объекты, цвет, нумерация, лимит примеров

Лист уже новый: несколько контуров, цвет по объектам, своя нумерация, примеры с ответом ≤ лимита.
Вариантов пока нет — число точек по-прежнему задаёт уровень (но уже через целевой поиск, см. ниже).

### 1.1 Объекты (группы контуров)

Новый модуль `dotdot/objects.py`. Вход: `prep.ink`, граф `g`, толщина линии `sw`. Выход: `edge_id → group`, метаданные групп (bbox, площадь, порядок).

1. Связные компоненты маски (8-связность), мусор уже отфильтрован в `prepare()`.
2. Для каждой компоненты — залитый силуэт (`binary_fill_holes`) и bbox.
3. Группировка (компоненты сортируются по площади силуэта, крупные первые):
   - **вложение**: центроид мелкой компоненты внутри залитого силуэта крупной → одна группа;
   - **близость**: зазор между пикселями ≤ `max(4, sw * 2)` px **и** площадь мелкой ≤ `0.25` площади крупной → одна группа. Два сопоставимых объекта рядом не склеиваются никогда;
   - иначе — отдельная группа.
4. Рёбра графа наследуют группу своей компоненты (скелет не пересекает компоненты): голосование по точкам ребра.
5. Порядок групп: первая — та, чья макушка выше всех (сохраняем правило «точка 1 на макушке»), остальные по порядку чтения (верх → низ, лево → право).
6. **Палитра — 6 цветов.** Если групп больше, самые мелкие присоединяются к ближайшей крупной, пока групп не станет ≤ 6: иначе два разных контура получили бы один цвет и обе нумерации с 1 — лист стал бы неоднозначным.

### 1.2 Контуры по объектам

`outline_edge_ids` работает по каждой группе отдельно: залитый силуэт группы → граница → рёбра группы у границы (порог 0.6, как сейчас). Внутренние детали группы — линиями.
Режим `all` — точками всё, но группы и цвет те же. Режим `auto` не меняется: `outline` для малыша, `all` для остальных.

### 1.3 Нумерация и цвет

`numbering`: `jumps` (одна цепочка, как сейчас) | `color` (по контурам цветом) | `series` (по контурам буквами).
**По умолчанию `color`** и в API, и в веб. При одном объекте `color` — это просто 1…N чёрным.

- Внутри группы нумерация сквозная по её линиям: 1…k, новая линия отмечается кружком (существующая легенда). Новая группа — снова с 1.
- `series`: буква на группу (A, B, C…), номер внутри группы. Раньше буква была на штрих — семантика меняется, это зафиксировано.
- `jumps`: сквозная нумерация через весь лист, цвет не используется (всё чёрное).
- Цвет несёт и точка, и подпись, и линия на листе ответа. Простые линии (детали) — чёрные.
- Палитра (тёмная, читаемая в 6.5–11 pt): `#1f5fbf` синий, `#d9480f` оранжевый, `#2b8a3e` зелёный, `#7048e8` фиолетовый, `#0b7285` бирюзовый, `#a61e4d` малиновый.
- Точка, общая для двух групп («6/68»), рисуется цветом первой группы; каждая подпись — своим цветом.

### 1.4 Целевое число точек и лимит примеров

- `build_plan` получает **цель**, а не только потолок: eps ищется бинарным поиском в обе стороны (`choose_eps` уже это умеет), при недоборе дробление длинных дуг (`maxseg`) усиливается до `dmin * 1.5`. Предел достижимого задают `dmin` и длина штрихов — цель усекается до него, факт возвращается в `stats.dots`.
- Новый параметр **`math_max`** (int, по умолчанию 100, допустимо 10–999). Действует только при `labels = math`:
  - чисел в группе (элементов `seq`, а не уникальных точек) ≤ `math_max`;
  - не влезает → упрощаем штрихи **этой** группы (поднимаем eps, снимаем `maxseg`), пока не влезет;
  - общее число точек листа из-за этого может оказаться ниже цели — это ожидаемо и показывается в интерфейсе фактом;
  - `MATH_ROOM` (отступ под широкую подпись) сохраняется.
- `math_expr` не меняется: ответ гарантированно ≤ `math_max`, потому что номер группы ограничен.

### 1.5 plan.json v2

```jsonc
{
  "v": 2,
  "page": {"w": 595.28, "h": 841.89},
  "image": {"w": 1000, "h": 760, "s": 0.52, "ox": 34.0, "oy": 120.0},
  "dotR": 2.0,
  "dots": [[x, y], ...],
  "paths": [[0, 1, 2, 0], [3, 4], ...],
  "groups": [0, 0, 1],          // НОВОЕ: группа на линию, индекс в colors
  "colors": ["#1f5fbf", "#d9480f"], // НОВОЕ: цвет на группу
  "lines": [[[x, y], ...], ...]
}
```

- `parse_plan` принимает v1 и v2. **v1 → каждая линия своя группа** (`groups = 0…len(paths)-1`), цвет чёрный: старая нумерация по штрихам сохраняется один в один, листы созданные до изменения живут ещё 24 ч и редактируются.
- Лимиты: `MAX_GROUPS = 6`, цвет строго `#rrggbb` (приходит из серверного плана родителя, но проверяется как любые внешние данные).
- `SeqItem` получает `group`; `series` остаётся индексом линии (его использует `labels.away_dir`). `Plan.groups` — группа на линию.

### 1.6 API

- `CreateJobDto`: `NUMBERINGS = ['jumps', 'color', 'series']`, новый `math_max` (`@IsInt @Min(10) @Max(999)`), нормализация: `numbering: 'color'`, `math_max: 100`.
- `EditJobDto`/`checkEdit`: принимает **`groups`** (длина = числу линий, целые в диапазоне групп). Без этого слияние/разрезание в редакторе рассинхронизирует группы с линиями: API делает `{...plan, ...checked}`. Цвета остаются от родителя — клиент их не присылает.
- `stats`: добавляется `contours` (число групп). `JobView.result.stats.contours` — в веб.
- Файлы и SSE не меняются.

### 1.7 Веб и редактор

- `model.ts`: `Draft` получает `groups: number[]`; все операции поддерживают его параллельно линиям:
  - `deleteDot` — убирает группы исчезнувших линий; `cutSegment` — обе части наследуют группу;
  - `mergeDots` (joined) — объединённая линия берёт группу первой; `startAt` — переставляет группы вместе с линиями;
  - `dotLabels(d, numbering)` — зеркалит воркер: `color`/`series` считают номер внутри группы.
- `Editor.tsx`: линии и точки в SVG цветом группы (`plan.colors[d.groups[i]]`), подписи — цветом своей группы; оранжевая подсветка инструмента «Добавить» остаётся оранжевой (это аффорданс, не данные).
- `Setup.tsx`: в «Тонкой настройке» — «Ответ в примерах не больше» (виден при `labels = math`), режим нумерации из трёх пунктов. Подсказки уровней больше не обещают конкретное число точек.
- `JobScreen.tsx`: третья метрика «контуров», когда групп > 1.
- i18n RU/EN: новые подсказки листа («Каждый цвет — отдельный контур, точки внутри него с 1»), легенда, тексты настроек.

### 1.8 Тесты этапа 1

- Воркер: синтетический рисунок из двух объектов и детали внутри одного → групп 2, деталь в группе родителя; `outline` даёт по контуру на объект; нумерация внутри группы с 1; в режиме примеров максимум номера группы ≤ `math_max`, крупный контур упрощён; групп не больше 6; plan v2 round-trip; v1 читается и даёт группу на линию; качество раскладки (наложений 0) в цвете; цель поиска eps достигается на простом и на плотном рисунке.
- Существующие: `test_generate_all_options` — добавить `color`; `test_dot_one_is_at_the_top` — первый номер первого контура на макушке; `test_fewer_pen_lifts` — для одного объекта по-прежнему 1 контур.
- API: валидация `numbering=color`, `math_max` вне диапазона → 400, правка с `groups` и без них.
- Веб: модель (группы через merge/cut/delete/startAt), редактор (цвета в SVG), i18n (паритет ключей), Setup (новые поля).

## Отклонения и уточнения по факту этапа 1

Что разошлось с текстом выше или уточнилось при реализации и проверке.

1. **Цель точек появилась уже в этапе 1.** `DOT_TARGET = {kid: 20, school: 60, adult: 130}` — те же числа, что `LADDER_BASE` этапа 2, одна константа на оба этапа. `MATH_ROOM` масштабирует не только потолок и отступ, но и цель.
2. **`_fit` ищет шаг дуг в обе стороны.** §1.4 описывал усиление дробления при недоборе; при переборе углов шаг приходится ещё и растягивать (бинарный поиск по `maxseg`), иначе цель не достигается: взрослый давал 62 точки вместо 130.
3. **Лимит группы жёсткий.** Цель упрощения группы = `math_max` минус замкнутые линии, а не `max(room, 2·линий)`: второе поднимало цель выше лимита (26 чисел при лимите 25 на among-us). Если даже минимум (2 числа на открытую линию, 4 на замкнутую) не влезает, короткие штрихи группы становятся простыми линиями. Контур по-прежнему не дробится.
4. **`colors` в `parse_plan` ограничен `MAX_PATHS`, а не `MAX_GROUPS`:** план v1 несёт по чёрному цвету на линию, и такие планы должны читаться.
5. **`render_edited` не применяет `math_max` и `MATH_ROOM`:** правка рендерит план как есть, лимит действует только при генерации.
6. **Выделенная точка в редакторе оранжевая**, а не цветом группы: аффорданс выделения, как подсветка инструмента «Добавить».
7. **Превью в Setup:** blob URL создаётся внутри `useEffect` — StrictMode монтирует эффект дважды и отзывал URL, созданный в `useMemo`.
8. **Подсказки уровней без чисел**, факт точек — в метриках результата; третья метрика «контуров» показывается только когда групп больше одной.

## Этап 2 — лестница вариантов

### 2.1 Расчёт

1. `POST /api/jobs` (как сейчас, multipart) → одна задача **`kind: 'analyze'`**, вход `<setId>/input.png`.
2. Воркер анализирует: объекты, штрихи в координатах листа, простые линии, геометрия, **реальный диапазон числа точек** `[dots_min, dots_max]` для данного уровня/режима/подписей (с учётом `math_max × групп`). Пишет `<setId>/scene.json`.
3. Воркер сам ставит в очередь задачи-варианты (`bullmq.Queue`), возвращает их id и цели. Анализ один раз, дублей нет.
4. Задача-вариант: `{id, kind: 'variant', input: '<setId>/scene.json', source: '<setId>/input.png', parent: setId, options: {..., target}}` — **без анализа картинки**, только точки + подписи + рендер (как текущая правка).

### 2.2 Лестница

```
LADDER_BASE  = {kid: 20, school: 60, adult: 130}
LEVEL_RANGE  = {kid: (20, 60), school: (60, 180), adult: (150, 350)}
шаг 1.35, 5 целей:  base * 1.35^i
```

- малыш: 20 · 27 · 36 · 49 · 60; школьник: 60 · 81 · 109 · 148 · 180; взрослый: 150 · 176 · 237 · 320 · 350;
- каждая цель усекается до `[dots_min, dots_max]` сцены, округляется, **дубли убираются** (простой рисунок → меньше вариантов, вплоть до одного);
- своё число T (`target` в «Тонкой настройке», 10–1000): три цели `0.8T / T / 1.25T`, диапазон уровня игнорируется, реальный предел сцены — нет;
- в режиме примеров верх лестницы дополнительно ограничен `math_max × групп`.

### 2.3 API, очередь, кеш

- `JobView` дополняется: `parent?: string`, `result.variants?: [{id, target, status, progress, result?}]`, `result.stats.{contours, dots_min, dots_max}`. У задачи анализа нет pdf — только сцена и список вариантов.
- SSE `GET /api/jobs/:id/events`: для набора поток живёт, пока **все** варианты не финальны; фильтр событий уже пропускает чужие `active`/`completed`, этого достаточно.
- Кеш: хеш картинки и параметров → id задачи анализа (повторная загрузка возвращает тот же набор с готовыми вариантами).
- Backpressure проверяется при загрузке; дочерние задачи ставит воркер (их ровно ≤ 5). **Нагрузка на загрузку ×5**: пересмотреть `MAX_WAITING_JOBS`/`RATE_CREATE_*` и заново замерить пропускную способность в README.
- Очистка: каталоги набора и вариантов удаляются тем же TTL по mtime; варианты ссылаются на `input.png` набора, правка копирует исходник в свой каталог (как сейчас).

### 2.4 Веб

- Адреса: `#/job/<setId>` — экран выбора, `#/job/<variantId>` — лист, `#/job/<id>/edit` — редактор. С листа кнопка «Другой вариант» ведёт в набор (`parent`).
- Экран выбора: карточки по числу вариантов — превью задания, цель и факт точек, статус (в очереди / считаем / готово / не получилось). Заполняются по мере готовности, выбрать можно сразу; ошибка одного варианта не ломает остальные.
- `Setup`: поле «Примерное число точек» (пусто = авто) и обновлённые подсказки уровней («5 вариантов на выбор»).
- `api.ts`: типы набора, `isFinal` для набора = все варианты финальны.

### 2.5 Тесты этапа 2

Воркер (лестница: усечение, дедупликация, своё число, режим примеров; scene round-trip; вариант рендерится без анализа), API e2e (загрузка → набор → варианты → файлы; кеш возвращает тот же набор), веб (карточки и их статусы, навигация набор → лист → редактор → назад, поля настройки).

## Отклонения и уточнения по факту этапа 2

1. **Дедупликация лестницы — не только точные дубли.** Цель усекается до предела рисунка, и верхние ступени слипаются: 148 и 150 точек дают один и тот же лист. Ступень отбрасывается, если она ближе 5 % к предыдущей (`ladder_targets`). На among-us взрослый даёт 4 варианта (150/176/237/320), школьник — 4 (60/81/109/148), а не 5. Простой рисунок из двух объектов — 2 варианта.
2. **Своё число центрируется, но тоже усекается и дедуплицируется:** `target=100` на among-us дал 3 цели (80/100/125) — все три влезли в предел рисунка.
3. **`options.target` в проводе — `null`, когда число автоматическое** (`asdict(Options)` в статистике анализа). Веб считает авто и `null`, и отсутствие поля; в формуляр `target` не отправляется вовсе, чтобы кеш не различал «авто» и «пусто».
4. **Экран анализа — обычный «Waiting».** Как и решено в ручке 11: пока идёт анализ, показываем прогресс задачи; полка появляется, когда у набора есть `result.variants`, и карточки заполняются по мере готовности.
5. **Все варианты упали → экран ошибки**, а не пустая полка: код берётся у первого упавшего варианта. Один упавший вариант среди готовых — карточка с текстом ошибки, остальные выбираются.
6. **«Другой вариант» ищет набор по цепочке `parent`** (`findSetId`, до 5 переходов): у листа-варианта родитель — набор, у правки — лист. Прямой ссылки на набор в `JobView` нет, лишний запрос дешевле ещё одного поля в каждом ответе.
7. **Пропорции превью — от первого загруженного листа** (`--shot-ratio`): листы бывают альбомными (A4 landscape), портретная заглушка растягивала бы картинку. Пока ни одна не загрузилась — 210/297.
8. **Полка — flex-wrap, а не сетка на 5 колонок:** карточка `max-width: 13rem`, последний ряд по центру. Иначе 2–3 варианта растягивались бы на всю ширину. На 390 px получается 2+1, миниатюра исходника скрыта.
9. **Число на карточке — факт, пока считается — цель:** готовая карточка показывает `stats.dots` (138 при цели 150), считающая — «≈150»; если факт отличается от цели, под числом «цель N». Ключи и testid карточек — по цели, не по факту.
10. **Лимиты от наплыва пересмотрены, числа оставлены.** `MAX_WAITING_JOBS=300` считает задачи очереди, а не загрузки: загрузка — это анализ плюс до 5 вариантов, т.е. предел ≈ 50 загрузок. `RATE_CREATE_PER_MIN=10` / `_PER_HOUR=60` на IP: десять загрузок в минуту — это ~60 задач, около 1/8 мощности двух воркеров, один IP сервер не занимает. Замер (условия и числа — в README «Local load check»): 40 загрузок разом → 160 листов за 20 с, пик очереди 157 задач, ошибок нет; анализ ~0,11 с, рендер варианта ~0,21 с. Набор стоит ~1 с CPU — примерно три прежних листа, а не пять: анализ общий, вариант не читает картинку.

## Проверка

Гибрид, как договорились: Redis и воркер в Docker (исходники воркера примонтированы — правки без пересборки), API и web локально.
Порт 6379 на машине занят другим проектом, поэтому dev-Redis слушает 6380.

```bash
mkdir -p /tmp/dotdot-data
docker run -d --name dotdot-redis-dev -p 6380:6379 redis:7.4-alpine \
  redis-server --appendonly yes --save "" --maxmemory-policy noeviction
docker build -t dotdot-worker-dev services/dots-worker
# --user обязателен: образ работает под uid 10001 и не сможет писать в каталог, созданный вашим пользователем
docker run -d --name dotdot-worker-dev --network host --user "$(id -u):$(id -g)" \
  -v "$PWD/services/dots-worker:/app" -v /tmp/dotdot-data:/data -e HOME=/tmp \
  -e REDIS_URL=redis://localhost:6380 -e STORAGE_DIR=/data dotdot-worker-dev

# тесты воркера — в контейнере: cv2 и cairo есть только там
docker run --rm -v "$PWD/services/dots-worker:/app" -w /app -e HOME=/tmp \
  --entrypoint python dotdot-worker-dev -m pytest -q

# API локально; после правок пересобрать и перезапустить, иначе отдаётся старый dist
cd apps/api && npm run build \
  && REDIS_URL=redis://localhost:6380 STORAGE_DIR=/tmp/dotdot-data PORT=3000 CORS_ORIGINS='*' node dist/main.js
npm test

# e2e сам поднимает Python-воркер: нужен образ с Node 22 + cairo + pytest.
# dotdot-e2e — это образ воркера с добавленным Node; собран ad hoc, Dockerfile в репозиторий не добавляли
docker run --rm --network host -v "$PWD:/repo" -w /repo/apps/api \
  -e TEST_REDIS_URL=redis://localhost:6380 -e HOME=/tmp --entrypoint bash dotdot-e2e:latest \
  -c "npx vitest run --config vitest.e2e.config.ts"

# web локально
cd apps/web && npx tsc --noEmit && npm test && npm run dev   # :5173, /api → :3000
```

Счётчики: воркер **121**, API **10 + 9 e2e**, веб **45**.

В браузере проверено: два объекта на одном рисунке (цвет, своя нумерация, примеры ≤ лимита), три режима нумерации, редактор сохраняет группы после слияния и разрезания, цветной лист ответа, ч/б буквами читаем. Этап 2: полка вариантов (4–5 карточек на уровне, 2 на простом рисунке, 3 на своё число), заполнение по мере готовности без перезагрузки, ошибка одного варианта не мешает остальным, навигация полка → лист → редактор → лист → полка, RU/EN, светлая и тёмная темы, раскладка на 390 px.

## Открытые ручки

Решения, которые я принял сам — этапы закончены, но оспорить их можно и сейчас.

1. **Палитра 6 цветов** и склейка мелких объектов при превышении. Альтернатива — печатать буквы вместе с цветом (дублирование маркеров).
2. **Дальтонизм**: своя нумерация в каждом цвете может путать при неразличимых цветах. Обход — режим букв; третий маркер (форма точки) не делаем.
3. **Касающиеся объекты** (кот на коврике) сливаются в один контур: разделение watershed/сегментацией не делаем.
4. **Промежуточные числа в вычитании** могут превышать лимит: при лимите 100 возможен пример «109−9». Ограничение только на ответ — как выбрали; если нужно, ограничим и operands.
5. **Порог близости** `max(4, sw*2)` px и доля площади `0.25` — подобраны на глаз, проверим на реальных рисунках и поправим.
6. **Общая точка двух групп**: цвет точки — первой группы, подписи каждая своим цветом.
7. **Ручная перегруппировка и перекраска** в редакторе — отложено (выбран автоматический режим).
8. **«Скачать все варианты одним PDF»** — не делаем.
9. **Имя параметра `math_max`** (snake_case) в проводе, DTO и веб-форме — остальные параметры однословные, единообразия нет.
10. **Старые листы** (plan v1) живут 24 ч и редактируются: каждая линия становится своей группой, прежнее поведение сохраняется.
11. **Экран «нашли N контуров»** до вариантов не делаем: фаза анализа показывается как обычный прогресс.
12. **Набор вместо одного листа** — страх «пропускная способность упадёт в 5 раз» не подтвердился: анализ общий, вариант рендерит без картинки, набор стоит ~3 прежних листа. 40 загрузок разом → 160 листов за 20 с, ошибок нет (README «Local load check»). Лимиты от наплыва оставлены прежними, см. отклонение 10 этапа 2.
