# Решения по MVP

| Тема | Решение |
|---|---|
| Что превращать в точки | Выбор пользователя: всё точками / только контур (детали линиями). По умолчанию: «малыш» — только контур, «школьник» и «взрослый» — всё точками |
| Нумерация нескольких линий | Выбор пользователя: сквозная с «прыжками» (по умолчанию) / отдельные серии |
| Сложность | Ползунок «малыш / школьник / взрослый» (~20 / 60 / 150+ точек) |
| Подписи | Цифры или математические примеры (выбор пользователя), в MVP |
| Ручной редактор точек | v2 |
| Формат результата | PDF A4 (+ лист-ответ); остальные форматы в v2 |
| Языки | RU + EN |
| Хостинг | VPS, docker compose |
| Очередь | Redis + BullMQ (Nest `@nestjs/bullmq`, Python `bullmq`) |
| Алгоритм | Python + OpenCV + scikit-image, горизонтальное масштабирование воркеров |
| Донаты | CloudTips (основной для РФ), опционально Boosty; Ko-fi для EN — ссылки в конфиге |
| Маскот | Dottie — дружелюбная точка с глазками |

## Алгоритм v0 — результаты на Among Us

| Режим | Точек | Время |
|---|---|---|
| малыш, только контур | 48 | ~0,45 с |
| школьник, всё точками | 128 | ~0,55 с |
| взрослый, всё точками | 255 | ~0,9 с |

Примеры: [docs/samples](samples).

## Алгоритм v1 — меньше отрывов, чище подписи

| Уровень | Отрывов v0 → v1 | Двусмысленных подписей v0 → v1 |
|---|---|---|
| малыш | 16 → 9 | 0 → 0 |
| школьник | 22 → 15 | 2 → 0 |
| школьник, примеры | 22 → 15 | 14 → 0 |
| взрослый, примеры | 23 → 19 | — → 1 |
| взрослый | 23 → 19 | 18 → 1 |

Наложений подписей друг на друга, на точки и на линии — 0 во всех режимах.

## Старт нумерации

Точка 1 всегда на макушке рисунка. Замкнутая линия просто поворачивается к верхней точке (бесплатно), открытая разрезается в ней на две ветки, обе начинаются с точки 1 (+1 отрыв).

## API и очередь

| Тема | Решение |
|---|---|
| API | NestJS 12 (только ESM), `@nestjs/bullmq`, Node.js 22 (нужен зависимостям Nest 12); тесты — Vitest + SWC |
| Связь API ↔ воркер | BullMQ поверх Redis: задача `{id, input, options}`, результат — пути к файлам; статусы через QueueEvents |
| Статус в браузере | SSE `/api/jobs/:id/events` (один поток QueueEvents на реплику), запасной вариант — опрос `GET /api/jobs/:id` |
| Хранилище файлов | Общий Docker-том `/data`, TTL 24 ч. MinIO не берём: бесплатная версия больше не развивается, репозиторий в архиве. Интерфейс хранилища маленький — S3-драйвер (Garage, SeaweedFS, облако) можно добавить позже |
| Устойчивость к наплыву | Реплики API за Caddy, воркеры по одному ядру, лимиты по IP в Redis, `429 BUSY` при длинной очереди, кеш по хешу картинки и параметров, Redis `noeviction` + AOF |
| Ошибки | Единый формат `{error: {code, message}}`, тексты для людей — в веб-интерфейсе |

## Веб-интерфейс

| Тема | Решение |
|---|---|
| Стек | Vite 8, React 19, TypeScript; без UI-фреймворка — свой небольшой CSS (OKLCH-палитра «тёплая бумага», светлая и тёмная темы); иконки lucide-react; шрифт Nunito (кириллица) лежит в сборке, без внешних CDN |
| Размер | ~81 КБ JS gzip |
| Состояние | Задача в адресе `#/job/<id>` — перезагрузка и ссылка работают сутки. Ничего не хранится в браузере |
| Статус | SSE, при обрыве — опрос раз в 1,5 с; позиция в очереди и прогресс |
| Тон | Маскот Dottie (радуется / думает / растерян), дружелюбные тексты для каждой ошибки, правильные склонения по-русски |
| Язык листа | Следует за языком интерфейса, пока пользователь не выберет сам |
| Пример | Своя рыбка вместо Among Us: картинку HeartColoring публиковать нельзя |
| Донаты | Карточка после результата и ссылка в подвале; для RU сначала CloudTips, для EN — Ko-fi; без ссылок карточка скрыта |
| Раздача | Отдельный контейнер `web` (Caddy, `:8080`), кеш `immutable` для `/assets/*`, `no-cache` для остального |

## Исправлено: задержка подхвата задач воркером

redis-py 8 у асинхронного клиента по умолчанию ставит `socket_timeout=5` — ровно столько BullMQ ждёт новую задачу (`BZPOPMIN`, 5 с). Клиент рвал соединение в момент ответа Redis и переподключался с паузой: новые задачи ждали до ~10 с, одна зависла на ~75 с. Воркер теперь добавляет `socket_timeout=30` к `REDIS_URL` (если он не задан явно). Подхват — 0,01–0,03 с.

## Редактор точек

- После генерации воркер пишет `plan.json`: `{v:1, page{w,h}, image{w,h,s,ox,oy}, dotR, dots[[x,y]], paths[[ids]], lines[[[x,y]]]}`. Координаты — в пунктах листа A4; замкнутые линии повторяют первую точку в конце; `image` переводит пиксели загруженного файла в координаты листа (с учётом уменьшения до 1600 px и обрезки полей).
- Редактор (SVG в координатах листа) меняет только `dots` и `paths`; нумерация, подписи и стартовые кружки пересчитываются из порядка точек — то же правило, что в генераторе.
- `POST /api/jobs/:id/edit` создаёт новую задачу: API берёт `lines` и `page` у родителя, копирует исходник в новую папку (чтобы можно было править правку), воркер пропускает анализ изображения и только рендерит — 0,3–0,9 с.
- Упрощение линий делается только при первой генерации, чтобы повторные правки не «уплывали».
- Листы, созданные до редактора (без `plan.json`), редактировать нельзя — интерфейс это честно объясняет.
- Слияние («Слить»): нажать точку A, затем B — A встаёт на место B. Концы двух разных открытых линий соединяются в одну линию (меньше отрывов), концы одной линии замыкают её. Остальные случаи — одна общая точка с двумя номерами («6/68»), её можно «Разъединить» обратно. Соседние повторы и «петли» из двух точек убираются.
- Разрезание («Разрезать»): нажатие на отрезок удаляет связь между двумя точками. Открытая линия делится на две, вторая идёт сразу за первой в нумерации и начинается с кружка; замкнутая линия размыкается в месте разреза. Точка, оставшаяся без линии, удаляется. Сами точки разрезать нельзя — только отрезок между ними; на плотных листах зона попадания по точке в этом режиме уменьшена.
- Сервер ничего нового не требует: формат `paths` уже допускал повторы точки внутри и между линиями.
- Найдено при проверке: подложка смещалась (не учитывались масштаб и обрезка в `prepare()`) — исправлено и закрыто тестом; в PNG-превью у цифр была цветная субпиксельная кайма — теперь сглаживание в оттенках серого.

## Контуры, цвет и лимит примеров (этап 1)

- Объекты: связные компоненты маски + вложение и близость (`dotdot/objects.py`); не больше 6 групп, мелкие склеиваются с ближайшей крупной. Цвет = объект, нумерация внутри объекта с 1.
- Нумерация: `jumps` / `color` (по умолчанию) / `series`; буква серии теперь на объект, а не на штрих.
- Число точек: цель уровня `DOT_TARGET` = 20 / 60 / 130, поиск допуска и шага дуг в обе стороны. Замер на тестовых рисунках: малыш 19/20, школьник 59/60, взрослый 127/130; наложений подписей 0.
- `math_max` (10–999, по умолчанию 100): лимит на ответ, только в режиме примеров. Крупный контур упрощается сам; если даже минимум чисел не влезает, короткие штрихи контура уезжают в простые линии — лимит не нарушается никогда.
- plan.json v2: `groups` на линию и `colors` на объект; v1 читается как «группа на линию, всё чёрное», старые листы живут и редактируются.
- Редактор проводит группы через слияние, разрезание, удаление и «сделать первой»; линии, точки и подписи — цветом контура. Выделенная точка оранжевая (аффорданс).
- Правка не переприменяет `math_max`: лимит действует при генерации, дальше номера — ответственность пользователя.
- Проверка: воркер 109 тестов, API 10 + 8 e2e, веб 37; в браузере — два объекта, три режима нумерации, лимит 25, правка с сохранением цветов.

## Лестница вариантов (этап 2)

- Одна загрузка = **набор**: задача `analyze` считает сцену один раз (`scene.json` — объекты, штрихи в координатах листа, простые линии, реальный предел точек) и сама ставит в очередь задачи-варианты. Вариант рендерит без анализа картинки.
- Лестница: цель уровня (20 / 60 / 130) × 1,35^i внутри диапазона уровня (20–60 / 60–180 / 150–350). Своё число T (`target`, 10–1000) даёт три цели 0,8T / T / 1,25T, диапазон уровня игнорируется. Каждая цель усекается до предела рисунка; дубли и ступени ближе 5 % к предыдущей убираются — 148 и 150 точек это один лист. На among-us школьник и взрослый дают по 4 варианта, простой рисунок из двух объектов — 2.
- Уровень теперь про оформление (радиус точек, шрифт, мин. отступ, порог деталей, сложность примеров), число точек — отдельная ось. Подсказки уровней обещают «пять листов на выбор», а не конкретное число.
- Веб: полка карточек `#/job/<setId>`, лист `#/job/<variantId>`, редактор `#/job/<id>/edit`. Карточка — превью, факт точек (цель, пока считается), бейдж «как для уровня» / «ваше число», статус; заполняется по мере готовности, ошибка одного варианта не ломает остальные. С листа «Другой вариант» возвращает на полку: набор ищется по цепочке `parent` (у правки родитель — лист).
- API: `JobView.parent`, `result.variants[]` со своими статусами и файлами, `stats.{contours, dots_min, dots_max, targets}`. SSE набора живёт, пока все варианты не финальны. Кеш по хешу картинки и параметров возвращает тот же набор с готовыми листами.
- Пропорции превью в полке — от первого загруженного листа (`--shot-ratio`): листы бывают альбомными. Полка — flex-wrap с центрированным последним рядом, а не сетка на 5 колонок: два варианта не растягиваются на всю ширину.
- Лимиты от наплыва пересмотрены и оставлены прежними: `MAX_WAITING_JOBS=300` считает задачи очереди (загрузка даёт до 6 задач, т.е. предел ≈ 50 загрузок), `RATE_CREATE_*` — 10/мин и 60/час на IP (~60 задач/мин, около 1/8 мощности двух воркеров). Замер: 40 загрузок разом, 2 воркера по 1 CPU → 160 листов за 20 с (~2 набора/с, ~8 листов/с), пик очереди 157 задач, ошибок нет; первый лист набора p50 11 с, весь набор p50 12 с / p95 20 с. Анализ ~0,11 с, рендер варианта ~0,21 с: набор стоит ~3 прежних листа, а не 5 — анализ общий.
- Проверка: воркер 121 тест, API 10 + 9 e2e, веб 45; полка проверена в браузере — заполнение вживую, своё число, ошибка одного варианта, навигация туда-обратно, RU/EN, светлая и тёмная темы, 390 px.

## Стратегии определения объектов (этап 3)

- Блокером оказались не режимы, а **группировка рисунка на объекты**: пока группы неверны, `mode` бессмысленен. Стратегия = способ определения объектов, `mode` не тронут. Новая опция `strategy`: `auto` / `subject` (весь рисунок — один объект) / `classes` (объект + повторяющийся декор) / `components` (прежнее поведение, базовая линия). Кеш API и так ключуется по параметрам — новая опция разделяет его сама.
- Предобработка удаляла сам рисунок: правило «крупный разреженный компонент = рамка» подходило персонажу (заполнение bbox 0.05–0.11). На 4 из 5 реальных картинок оставались одни зрачки, на bold — `strokes=0` и падение всех вариантов. Теперь рамка = компонент, который **прилип к кромке своего bbox и пуст внутри** (`near > 0.9`, `inner < 0.02`): рамка 1.000/0.000, персонажи 0.018…0.092/0.473…0.702 — запас большой. Заодно убираются линейки на всю ширину и строки подписи («Step 7» давала два объекта со своим цветом и нумерацией с 1). Порог спеклов не поднимали: 14.5 px против 88–260 px у лучей солнца.
- Признаки (`dotdot/features.py`) считаются один раз и едут в `scene.extra` и `stats` — версия `scene.json` не менялась. Главное: `dominance` по **залитым силуэтам после вложения**, а не по сырым чернилам (step7: 0.583 → 1.000), и `cycle_rank = E − V + C` вместо отдельного прохода за дырками (совпал с числом замкнутых областей на всех замеренных картинках).
- Автовыбор: `subject` = `dominance`, если `n_roots ≤ 2`, иначе 0; `classes` = 0.6 + 0.2·min(`n_classes`, 2)/2; `components` = 0.5. Условие по корням защищает тыкву: одной `dominance` = 0.852 хватило бы для неверного `subject`. На 19 картинках: 9 `subject`, 10 `classes`. Ручной override — в «Тонкой настройке» и чипами на полке; имя и признаки видны в `stats`.
- Классы подобия (площадь / пропорции / заполненность) + тест сворачивания «не большой и далёкий»: тыква **6 непоследовательных объектов → 4 согласованных** (тыква / 4 листа / 5 звёзд / кружки линиями), четыре одинаковых листа больше не обрабатываются по-разному. Сопоставимые и далёкие объекты (облака) не сворачиваются. Свёрнутый класс никогда не поглощается близостью — в этом весь смысл; кэп палитры склеивает целые классы и не разрывает их.
- Страховка мостов: невидимый мост допускается только внутри одной **связной компоненты**, а не просто одной группы — иначе два близких декора в одной группе получали бы реальный штрих между собой.
- Сплошные области (зрачки, 3 из 5 картинок) скелетизировались в чёрточку. Теперь `ink/filled ≥ 0.85` → замкнутый полигон, который **печатается залитым на обоих листах**, без точек и подписей. `solids` — опциональный ключ `plan.json` (v2 не менялся: API жёстко пишет `v: 2`), в редакторе — нередактируемый слой, при правке сохраняется.
- Сравнение — **по листу-ответу**. Офлайн: `tools/compare.py` (19 картинок × 4 стратегии = 76 прогонов, 0 падений), метрика `ink_coverage` — recall/precision растеризованного ответа против очищенной маски с допуском 1 px; контактный лист и отчёт пишутся вне репозитория. В вебе: тумблер «Пазл / Ответ» на полке и чипы стратегий — клик создаёт новый набор, возврат к прежней стратегии мгновенный (~0,8 с, кеш).
- Честный замер покрытия: recall 0.34–0.75 при цели уровня и 0.42–0.97 на максимуме диапазона, наложений подписей 0 во всех 76 прогонах. Ограничитель — **бюджет точек**: на детальных сценах `dots.simplify` превращает дуги в хорды. Поэтому предпроход замкнутых граней (шаг 7 плана) срезан по его же правилу: он меняет группировку путей, а не то, какие рёбра нарисованы, и recall не поднимет.
- `samples/among-us.png` не пострадал: рамка и персонаж разделяются новым правилом, зрачки не проходят порог сплошности, группировка `components` совпадает с прежней (закрыто тестом). Реальные JPEG не коммитим — `tests/test_real_images.py` под `DOTDOT_SAMPLES` проверяет инварианты и измеренные полы покрытия, а не золотые пиксели.
- Проверка: воркер 153 теста + 19 на реальных картинках, API 10 + 10 e2e, веб 49, `tsc` чист; в браузере — bold даёт настоящий пазл с залитыми зрачками на обеих страницах PDF, тыква 4 объекта против 6 у `components`, тумблер ответа, чипы стратегий и кеш, статический бейдж после перезагрузки, залитые полигоны в редакторе, RU/EN и тёмная тема. Скриншоты и раскладку 390 px проверить не удалось: поверхность браузера в приложении была недоступна.

## Распределение бюджета точек (этап 4)

- Бюджет уровня не хватал на рисунок в ~5 раз (честная стоимость при допуске уровня — в среднем 299 точек против цели 60), и алгоритм размазывал точки по всему рисунку хордами. Теперь в `all`/`auto` бюджет **делится между штрихами** (`dots.allocate`): важность = длина, штрих, который не может унести `DOT_FLOOR = 5` точек, печатается линией; допускается самый длинный префикс, чья доля ≥ порога. `outline` не тронут. Лист-задание честно говорит второй строкой шапки: «Часть рисунка уже напечатана линиями — соединяй только точки.» (на листе ответа строки нет).
- Квота тратится на изгибы (свой допуск штриха, чистый RDP); доля больше изгибов дробит дуги (`_fit` с `maxseg` уровня) — чистый RDP не добирал точки на гладких формах. Порог проверяется **по факту** после подгонки: `dmin` и квантование RDP ломают обещание квоты, такой штрих уезжает в линии. Рисунок без изгибов всё равно даёт головоломку (fallback на все штрихи).
- Water-filling остатка нужен **до** допуска, а не после: прежний замер «не нужен» перераспределял остаток, когда девать его было некуда. До допуска among-us на 215 точек допускает 15/15 штрихов вместо 10/15; излишек при полном допуске раздаётся по длине.
- Лестница привязана к рисунку: низ — цель уровня, верх — `min(scene.dots_max, потолок)`, шаг `max(1.35, геометрический)`. Потолки: kid 50, school 300, **adult 300** (не 600, как планировали): ёмкость подписей — свойство листа A4. Замер на худшем рисунке: 276 точек — 0 наложений/15 ambiguous, 366 — 1/47, 552 — 28/215 (лист нечитаем, проверено глазами). Диапазоны: 20–60 / 60–300 / 150–300.
